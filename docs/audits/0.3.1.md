# Security audit: host-guard 0.3.1

Open confirmed findings: 0

| | |
|---|---|
| Tool | [security-audit skill](https://github.com/cloudflare/security-audit-skill) by Cloudflare, commit `c1c8a8c` |
| Scope | the changes since 0.3.0 (`v0.3.0..` the 0.3.1 branch): the package self-check, `ci/package_audit.py`, `ci/verify_pypi.py`, the release and CI workflows, the red team and cloud tests on the wheel, the lifecycle test |
| Run | `quick` profile scoped to the diff: 3 hunters, a coverage critic, a fresh verifier per candidate; both validators pass |
| Result | 2 confirmed (1 medium, 1 low), 1 needing validation, 2 rejected; all addressed below |

## Confirmed, fixed

| # | Severity | Finding | Fix |
|---|---|---|---|
| 1 | medium | The package audit and the PyPI check could never fail their step: each was piped into `tee`, and the default step shell has no `pipefail`, so the step took `tee`'s exit code | both workflows run every step with `shell: bash` (`bash -eo pipefail`); checked: a failing audit now fails its step |
| 2 | low | The drift check compared only `host_guard/payload/*` and files directly in `host_guard/`: a wheel that also carried `host_guard/manager/__init__.py` (which would win over `manager.py` and run as root) passed | every wheel file outside its metadata must map to a repository file; the build backend is pinned (`setuptools==80.9.0`); checked with exactly that planted file |

## Needing validation: closed

| Lead | Decision |
|---|---|
| A tag push runs the `release.yml` of the tagged commit, so whoever can push tags could drop the "tag is on main" gate | GitHub settings: a tag ruleset lets only repository admins create, move or delete `v*` tags, and the `pypi` environment deploys only from `v*.*.*` tags. The repository has one writer, its owner |

## Rejected, hardened anyway

| Claim | Why rejected | Hardening done |
|---|---|---|
| The package self-check can be bypassed (rewrite RECORD, links, delete metadata, edit `manager.py`, race the copy) | every way needs write access to the root-owned pipx install, which red team PKG-4 checks; no one below root crosses into root | RECORD is read directly and a missing one fails closed; any link in the payload is refused; missing files are reported; the docs now say plainly that it catches accidents and non-root changes, not root |
| `Requires-Dist` matched only in one letter case | only a malicious build backend could write it, and that already runs code | matched in any case |

Also hardened: every action in every workflow is pinned by commit (`download-artifact` and `upload-artifact` in the jobs with `id-token` and `contents: write`, CodeQL's too); `verify_pypi.py` prints "attested" only when it is and never hands a mismatching file to the install tests.

Not covered by this scoped pass: code unchanged since 0.3.0 (see [0.3.0.md](0.3.0.md)), and GitHub and PyPI settings beyond the two named above.
